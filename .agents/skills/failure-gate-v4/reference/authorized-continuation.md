# Carry authorized work forward without assuming the next grant

Normative throughout this skill: discovery, planning, installation, operation,
validation, investigation, recovery, confirmation and reporting. Apply actual
ACTIVE/INACTIVE/UNKNOWN policy, current approved task/plan and transitive scope,
finite budgets, evidence and lifecycle requirements. This reference adds an
Agent obligation to continue and prepare; it adds no authority or host interface.

## 1. Finish the work already authorized

Agent must continue all remaining feasible implementation, review and verification
within the current approved scope, available capabilities and remaining budgets.
Do not stop at a source checkpoint or return routine instructions for work the
Agent can already perform. A partially staged component is not finished Stage A.
Inspect the actual approved scope before deciding that further work needs approval.
Continue independent permitted work when another path is blocked; preserve
resource exclusion and do not call conflicting work independent merely by label.

Feasible does not mean authorized. Inert staging may allow source/document writes
but forbid imports, syntax checks, tests, builds, store initialization, wiring,
service changes and signals. Do not perform those checks because they are short,
normally routine, or described as review. Task-wide edit/test gates remain binding
until an explicit authorized amendment; record the actual revised plan/digest.
Stage A may finish permitted supervisor/gate code while Stage B execution waits.
Finish a bounded approved task when its outcome is established; no endless extra
confidence checks, automatic successors, recurring work or speculative expansions.

## 2. Carry planning across a real boundary

At an authorization, capability, safety, evidence or budget boundary, block only
the dependent action and identify the exact missing requirement. Agent must
proactively prepare the next concrete scoped proposal using permitted planning
and evidence access. Do not wait for the user to supply follow-up wording, invent
technical routes, or ask broadly whether to investigate what can already be read.
Distinguish verified facts, reported findings, hypotheses and unperformed checks.
If preparing a proposal itself exceeds approved read/write scope, state that
boundary and request only the specific decision needed; no unauthorized probing.
An inaccessible external source is not permission to demand secrets or bypass it.

Ask only for the specific approval or decision needed. Reuse current applicable
approval; do not demand approval again for unchanged permitted work. Never treat
silence, status, proposed policy, remaining launch slots, a file reference or this
skill amendment as consent. Discover and propose real mappings, not invented APIs.
Preparation is not execution authorization. No automatic task creation,
status/dependency change, approval, activation, retry, budget renewal, recovery,
coverage waiver, policy change, cutover, publication, merge or deployment.
Use an actually available authorized host interface only within its real scope.

## 3. Required next-proposal contents

Record applicable fields and explicitly mark unknown/unavailable ones:

- Exact task/operation/stage and requested approval; current governing policy,
  actual approval source, versions and plan/decision bindings.
- Current canonical source closure/manifest and tested versus untested revision;
  commands, selectors, targets, transitive callers and permitted side effects.
- Actual capability/prerequisite mappings and responsible integration role;
  independent supervision/admission/termination and resource/conflict boundaries.
- Complete finite phase/session/parent/attempt limits and remaining consumption;
  permitted launches/repetitions/retries, cancellation and bounded evidence capture.
- Acceptance criteria and proof type, expected injected failures versus failed
  acceptance, raw outcomes, acknowledgements and retained incidents/exclusion.
- Explicit exclusions, unresolved risks and exact scope amendment if needed;
  work already permitted, work awaiting approval and the following contingent step.

Refresh source/plan bindings after approved changes; do not silently carry old
approval to a changed closure. A proposal may cover multiple explicit scopes and
conditions, but its preparation does not approve any of them. Do not fabricate
message IDs, task IDs, endpoints, approvals, records, tests or successful readback.

## 4. Stage and proof sequence

| Situation | Required next action within actual permission |
|---|---|
| Approved implementation is incomplete | Finish permitted source and review; report a checkpoint as partial, not complete. |
| Stage A source is complete; execution unapproved | Review by permitted means, pin source/evidence and prepare Stage B's bounded execution proposal; do not run checks. |
| First containment/supervision proof is unperformed | Specify safely admitted initial fixture proof and prerequisites, then later readiness checks; do not require those same proposed tests to have passed before a proposal can be prepared. |
| No safe independent boundary for first proof | Identify the actual missing safety capability and propose its scoped integration; neither waive it nor test an uncontained workload to prove safety. |
| Execution is authorized and safely admitted | Perform only admitted cases within verified limits, record truthful results and permitted repetitions; code presence alone is not readiness. |
| Execution fails or outcome is uncertain | Preserve raw failure, consumption and exclusion; continue only nonconflicting permitted work and prepare exact remediation/recovery or approval request. |
| Bootstrap readiness is proved | Discover/reuse or propose the ordinary deterministic policy and actual integration/caller-acceptance/cutover plan; bootstrap proof is not ordinary activation. |
| Ordinary work meets its approved requirements | Perform verified local acceptance/reporting; do not add a new approval, auto-merge or pretend platform completion is locally enforced. |

Only already authorized reruns/retries may execute; a maximum attempt count is
not permission for another attempt. Do not replenish counters, rename operations,
delete retained leases/sidecars or release unknown claims to continue. Negative
fixtures must use explicitly permitted nonconflicting isolation, preserve incident
evidence and shared parent accounting; they are not real retained-error recovery.
When the governing failure rule requires exactly three authorized isolation
retries, preserve it; insufficient safe authority/time blocks that classification.

## 5. Investigation, closure and completion

Read-only investigations do not become repair authority. Consult registered
evidence automatically, deliver the supported finding and prepare the smallest
scoped remediation proposal where needed. Do not run tests, install a monitor,
rewrite logs or create a repair task merely to answer an investigation.

Explicit owner-directed closure retains its existing exception: no second
approval, passing tests or new activation requirement. Perform already authorized
safe local/native steps, read back separate outcomes and report unresolved safety/
evidence; no automatic follow-up task or false validated completion. A missing
native interface is a factual blocker, not authority to invent a workaround.

Reports distinguish partial implementation, complete authorized stage, proposed
next work, awaiting approval, missing capability, executed fixture results, real
host acceptance, validated completion and owner-directed closure. State the
specific next approval/decision or capability owner when work remains blocked.
After an approved execution, proactively prepare the supported next proposal if
needed; do not repeat a generic blocker or invent readiness to keep moving.
Reference traversal occurs once per pinned canonical revision; no recursive loop.
